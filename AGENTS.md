# AGENTS.md

Instructions for every contributor to Emerald Co-Op: coding agents (Claude Code, Codex, ...) and the three humans (`bernardosevero`, `leomayca`, `DaviAlencastro`). Follow them so the repo stays consistent no matter who did the work.

## What this project is

A co-op mod for Pokémon Emerald: players see each other in the overworld (v1), later battle, trade and play together. Pieces:

- `rom/`: our fork of [pret/pokeemerald](https://github.com/pret/pokeemerald) (git submodule). New C code goes in `rom/src/coop/` and `rom/include/coop/`.
- `cmd/`, `internal/`: one Go module at the repo root (server, `fakeclient`, `symgen`). Standard library only.
- `client/`: mGBA Lua 5.4 scripts that bridge the game and the server.
- `docs/`: architecture, protocol, memory map, roadmap. **Read `docs/architecture.md` before your first task.**

Design decisions are recorded in `docs/architecture.md` and in the issues. Don't re-decide them in code. If you think one is wrong, comment on the issue and stop.

## Picking a task

Work comes **only** from GitHub issues in `BDL-Ltda/EmeraldCo-Op`. Board: https://github.com/users/bernardosevero/projects/5

You may only take an issue that meets **all** of these:

1. **Open and unassigned.** Never take an issue someone else is assigned to, even if it looks stale. Ask in the issue instead.
2. **Not blocked.** Every issue listed under `## Dependencies` ("Blocked by" / `#N`) is **closed**. On the board these show up in the **Ready** column, but check the issues themselves: the board can lag behind.
3. **Not an epic.** `type:epic` issues are placeholders for future versions. They get re-planned and broken down first. Never implement one.
4. **Earliest milestone first.** Prefer the lowest open milestone (`0.0` → `0.1` → ...), then the lowest issue number.

Use the `pick-task` skill (`.claude/skills/pick-task/SKILL.md`) to do this. It has the exact commands.

Once you pick an issue:

- Assign it to yourself (an agent assigns the human it's working for) and move it to **In progress** on the board.
- Take **one issue at a time**. Finish it (PR open) before picking another.
- Stay inside the issue's **Scope**. Anything in **Out of scope** belongs to another issue. If you find extra necessary work, open a new issue and link it. Don't silently expand the PR.

## Working rules

- **English everywhere**: code, comments, docs, commits, PRs, issues.
- **Never invent memory addresses.** Global addresses come from `client/addresses.lua` (generated by `cmd/symgen` from the ROM build). Struct offsets come from `docs/memory-map.md`, sourced from the decomp headers. No address literals anywhere else.
- **Never commit** ROMs (`*.gba`), saves (`*.sav`, `*.srm`, savestates), BIOS files, `.elf`/`.map` build outputs, `.bps` patches, or `client/config.lua`. The repo is public.
- **Never put secrets** (the server join key, public IPs) in the repo, issues or PRs.
- Keep it simple: no new frameworks or dependencies without a discussion in the issue first. Go uses the standard library. Lua tests use our tiny runner in `client/tests/`.
- Lua modules in `client/lib/` must stay pure (no `emu`, `socket` or `callbacks`) so they can be tested in CI.
- After any ROM change, rebuild and regenerate `client/addresses.lua` in the same PR.
- Update docs in the same PR when you change behavior, the protocol or the memory layout.

## Committing and opening PRs

**Before every commit and before opening a PR, use the `pre-commit` skill** (`.claude/skills/pre-commit/SKILL.md`). It covers:

- the commit message format: **Conventional Commits + gitmoji**, e.g. `feat(server): ✨ relay presence to other players`;
- the checks that must pass locally before a PR is opened (tests, lint, ROM build, forbidden files);
- the branch name and PR body format.

Right after opening a `feat` or `fix` PR, use the **`pr-walkthrough` skill** (`.claude/skills/pr-walkthrough/SKILL.md`): it creates an HTML page with diagrams explaining what changed and why, publishes it on the `walkthroughs` branch and links it in a PR comment, so reviewers can learn the change quickly.

Every change goes through a PR into `master` with one human approval. Never push to `master` directly, and never merge your own PR without that approval.

## Definition of Done

An issue is done when everything in its **Definition of Done** checklist is true. In short: acceptance criteria met, tests added, CI green, manual test result in the PR, docs updated, no forbidden files, approved by one human, merged with `Closes #N`.
