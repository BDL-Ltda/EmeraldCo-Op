Big picture

Two sources, never a guess

From 0.1 to 0.3 the Lua client reads the player's state straight from the game's RAM. AGENTS.md splits that knowledge in two. Global addresses come from symgen, which reads the ROM build's ELF and writes client/addresses.lua. Struct offsets are written by hand in docs/memory-map.md, sourced from the decomp headers.

This PR fills in the second half for the player, and adds the four globals the "visible" signal needs to the symgen allowlist.

How it works

Two pointer chases, redone every frame

Position and facing live in the player's object event. gPlayerAvatar.objectEventId picks one of the 16 entries in gObjectEvents, and each entry is 0x24 bytes. Map, gender and trainer ID live in the save blocks, which move. SetSaveBlocksPointers adds a random offset on every warp or full map load, at the start of every battle, and when a game is loaded. So the client has to re-read the pointer every time and never cache an address.

Under the hood

The visible signal, one condition at a time

visible is true only when all four conditions hold, and the client reads them every frame. Click a condition to see what it catches. The offsets and symbol values are the ones the PR verified. The independent review rebuilt the ROM and got the same values.

Decisions in this PR

Three choices worth checking

Offsets come from the compiler, not from reading headers

_Static_assert(offsetof(struct ObjectEvent,
currentCoords) == 0x10, "");
# + bitfield byte dumps, DWARF, disassembly
Why

Issue #9 requires it: bitfields such as facingDirection, which shares byte 0x18 with movementDirection, are easy to get wrong by eye. The offsets were checked three ways: disassembly of the real ELF, a scratch build with the exact modern flags, and DWARF. The review then repeated the asserts on its own clean build.

trainerId is read as two u16s, never one u32

tid = u16[sb2+0x0A] | u16[sb2+0x0C] << 16
# sb2 is 4-aligned, so +0x0A is only 2-aligned
Why

The save block's base is kept 4-aligned (load_save.c masks its random offset), so playerTrainerId at +0x0A is only 2-aligned. A single 32-bit read there would be misaligned, so the doc says to read two u16 values or four bytes instead.

Functions and a file-static in the symgen allowlist

gPaletteFade
sLockFieldControls
CB1_Overworld
CB2_Overworld
Why

The allowlist used to say "data objects only". The visible signal needs to compare function pointers stored in RAM, and it needs the control lock, which is a static. The new rules in symbols.txt allow these two cases only. symgen fails loudly on a name conflict or a missing symbol.
