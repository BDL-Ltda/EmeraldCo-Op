Big picture

The inbound ring finally has a reader

#22 built gCoopMailbox with an inbound ring (Lua → ROM), and #23 defined the PRESENCE payload with a slot byte. Until now nothing in the ROM consumed it. This PR adds that consumer, coop/remote_players.c, called once per frame from CB1_Overworld. It follows the #21 design (docs/remote-player-design.md) without changes.

How it works

Drain, then reconcile every slot, every frame

The module keeps no "spawned" flag. Each frame it finds slot n's object by local ID 228 + n and compares it with what the slot wants. The design calls this reconciliation: one rule handles camera culling, warps, battles, saves and Continue.

Under the hood

The inbound PRESENCE payload, as the ROM reads it

14 bytes, little-endian and unaligned, so remote_players.c reads it byte by byte. Layout from docs/memory-map.md (#23). Click a field.

Decisions in this PR

Mostly the #21 design, plus three small calls

Locked field: let the step finish, start nothing

// StepToward
if (ArePlayerFieldControlsLocked())
return;
ObjectEventClearHeldMovementIfFinished(obj);
Why

This is the design's review fix. FreezeObjectEvent skips objects with heldMovementActive, so a step in progress keeps playing. Clearing it would stop the sprite between tiles while currentCoords already names the target. So the module returns before clearing anything and catches up after the lock.

Forget every slot when Lua disconnects

// CoopRemote_DespawnAll
while (CoopMailbox_Pop(&msg)) ; // bounded
memset(sRemotes, 0, sizeof(sRemotes));
Why

A reconnect is a new session. Keeping old slots, or messages still queued in the ring, would draw players who may have left. The ROM pops and drops queued messages (moving only its own tail), so Lua must set lua_connected before its first push and resend every presence. This came from review and is documented in memory-map.md.

Create coop/overworld.c here

void CB1_Overworld(void) {
...
CoopOverworld_Update();
}
Why

The design has #24 create it, but #24 and #25 are in progress at the same time. The hook sits outside the callback2 check, as section 5 says, and the remote part checks callback2 itself. #24 only needs to add CoopPresence_Update();.
