How it works

Authenticate before replacing anyone

A new ID needs a free slot. An existing ID can reconnect at capacity, but only after supplying the correct key. Other players see the old session leave before the replacement joins.

Decisions

Small room, explicit ownership

A mutex orders membership events

The issue permits mutex or channel ownership. The mutex makes snapshots and leave-before-join ordering atomic for this five-player room. Each connection also serializes writes.

Limit

Writes hold the room lock and have a five-second deadline. Per-client queues and slow-reader isolation are still #14.

Configuration follows the wire limits

Flags override SERVER_ADDR, SERVER_JOIN_KEY and SERVER_MAX_PLAYERS. Capacity is 1–5 because protocol v1 welcome permits four remote entries. Invalid settings fail before listening.

Secrets

Help uses static text. Logs contain lifecycle fields, never raw messages, decoder errors or the key.

Resilience after review

Recover without dropping the room

  • Temporary Accept failures retry after 5 ms, doubling to 1 s. Success resets the delay, cancellation interrupts it, and permanent errors still return.
  • A transport reset during hello closes quietly; protocol errors and the hello deadline retain their documented error responses.
  • Unknown types log once per connection across both handshake phases. This bounds logs, not incoming traffic.
  • The shared protocol key validator replaces dummy hello data. Authentication uses constant-time comparison for equal-length keys; unequal lengths reject immediately.
  • SIGTERM now takes the graceful shutdown path. A Linux child-process test verifies successful exit; Windows command tests pass with signal delivery explicitly skipped.

Injected listener tests keep an authenticated player connected through temporary failures. Connection tests assert reset errors cause no write and no protocol-rejection log. The changed-trainerId reconnect case preserves #13's existing playerId replacement rule; trainerId is self-reported metadata.
