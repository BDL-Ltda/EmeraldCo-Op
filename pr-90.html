A whole party fits through the mailbox

Mailbox layout v2 lets the ROM and Lua exchange messages of up to 1024 bytes, split into 30-byte slots and streamed over several frames. Trading needs 600 bytes per side; PvP can reuse the same framing.

Big picture

A fragment layer on both ends of the same rings

Until now every mailbox message fit in one slot: a 2-byte header and 30 payload bytes. A ring holds at most 15 slots, which is 450 payload bytes, less than one party. This PR keeps the rings and the slot bytes as they are and adds a framing layer on each side: the ROM's mailbox.c and the new pure Lua module fragments.lua. The layout version goes from 1 to 2, so a v1.0 client and this ROM refuse each other.

How it works

Streaming 600 bytes through a 15-slot ring

A 600-byte message becomes 24 fragments of 26 data bytes (the last has 2). The sender pushes fragments until the ring is full and tries the same fragment again next frame; it never drops one. Each frame, presence goes out first, so it keeps flowing between fragments. The receiver copies each fragment into a 1024-byte buffer and delivers the message when the last byte arrives.

Decisions in this PR

Simple rules that let each side recover on its own

The header repeats in every fragment

else if (!sInMessage.active || type != sInMessage.type
|| length != sInMessage.length
|| index != sInMessage.nextIndex)
// drop the incomplete message
Why

It costs 4 of 30 bytes per slot, but each continuation can be checked on its own. A fragment from an abandoned message can never be glued onto a new one.

No message ID and no timeout

if (index == 0)
sInMessage.active = FALSE; // start over
Why

Each ring has one writer, so fragments arrive in order. A sender that gives up just stops, and the next message's fragment 0 drops the leftover. A disconnect resets both sides: the ROM abandons its outbound message when lua_connected is clear, and Lua clears its queue and reassembler on disconnect, reset and welcome.

Pumped from the overworld hook, for now

CoopPresence_Update();
...
CoopMailbox_PumpOutbound();
Why

Presence goes first, so a large message never delays it. Inbound messages are still read only while the overworld runs, as in v1. The trade screens (#80/#81) run outside the overworld and will need to call the pump and CoopMailbox_Receive themselves; the memory map says so.
