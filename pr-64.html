Big picture

The Lua half of the mailbox

From 0.4 the ROM owns co-op behaviour and Lua is a dumb pipe between gCoopMailbox and the socket. #22 added the ROM half: a header and two 16-slot rings in EWRAM. This PR adds the Lua half. Wiring it to the socket is left to #26.

How it works

Slot first, index last

Each ring has one writer and one reader, so there are no locks. Lua's frame callback can fire while the ROM is halfway through a mailbox call. Correctness then rests on ordering: the writer fills the whole slot before it moves head, and the reader copies the slot before it moves tail. push and pop follow the same rules as the C side and read both indices from memory on every call.

Under the hood

The PRESENCE payload

No C header defined this payload yet, so this PR sets the layout and records it in docs/memory-map.md#presence-payload. It is little-endian, packed with string.pack("<BBi2i2BBBI4"), and sits at slot offset 0x02. The example bytes are the test vector from mailbox_test.lua (map 0:9, x 7, y −1, facing east, visible, female, trainer ID 0xDEADBEEF). Click a field.

Decisions in this PR

Three choices worth checking

Memory is injected, never global

local box = mailbox.new(emu, addresses
.symbols.gCoopMailbox.addr)
# tests pass a table with read8/write8
Why

Required by the issue and by AGENTS.md (client/lib/ stays pure). The same object shape as emu means #26 can pass emu straight in.

Slot index appended, not reserved up front

encodePresence{..., slot = 3} -- 14 bytes
encodePresence{...} -- 13 bytes
Why

#25 needs a slot inbound and #24 has none to send. Adding it as the last byte keeps one shared layout and lets #25 use it without a layout change. Please confirm on the PR.

Indices re-read and range-checked on every call

if head >= 16 or tail >= 16 then
return nil, "...out of range..."
Why

A soft reset zeroes the mailbox. Caching tail or head in Lua would then read stale slots. An out-of-range index means the memory isn't a valid mailbox.

How it was tested

Fake memory in CI, real memory once

23 new tests use fake memory and small helpers that do what CoopMailbox_Push/Pop do. They cover empty and full rings, wrap-around past slot 15, write order, magic, version and rom_ready mismatches, and a presence round trip. Then I booted the #22 ROM (whose SHA1 matches addresses.lua) in mGBA with -g, dumped gCoopMailbox with gdb, and ran the module over the dump.
